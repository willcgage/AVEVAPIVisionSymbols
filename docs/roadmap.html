PVX symbol library — build plan

Plan complete — 30 symbols shipped through v1.5. Tier 3 is closed: one built, four declined with reasons.

AVEVA PI Vision 2019–2025 · library v1.5 · updated 9 August 2026

On where these ideas come from. The candidate list was informed by surveying what the commercial PI Vision symbol market sells, alongside AVEVA's documentation for what PI Vision 2025 ships natively. That survey is a map of what plant staff repeatedly ask for — which is not anyone's property, and neither are the chart types. Box plots, Sankey diagrams, Pareto charts, capability histograms and the Duval triangle are published, decades-old standard techniques.

What is proprietary is a vendor's source code, specific visual design, icons and branding. None of that has been read and none of it is obtainable — the commercial libraries ship obfuscated to paying customers. Every symbol here is specified from first principles against AVEVA's public extensibility API.

Two practical notes. Where a commercial product already solves a problem well and the licence is affordable, buying it is often the right call. That argument used to point at pvxEventGantt — the hard part being the PI Web API plumbing rather than the chart — which was true right up until the plumbing was built in v1.3. The reasoning stands even though the example no longer does. And do not ship a PVX symbol that is a visual clone of a specific commercial one: solve the problem, don't copy the answer.

Nothing matches those filters.

The plan is complete

Thirty symbols. Tiers 1 and 2 were built out through v1.4; tier 3 is now closed — pvxSlideshow shipped in v1.5 and the other four were declined rather than left open, each with the reason on its card. An item on a plan that nobody intends to build is a promise, and it is better to say so.

The one tier-3 symbol worth having turned out to be the one with an interesting problem in it. Navigating away destroys the symbol, so a slideshow cannot be a loop that runs: the same configuration is placed on every display in the rotation, and each copy reads the URL to work out which step it is on. Pause therefore has to outlive the navigation it exists to interrupt, which is why it lives in sessionStorage rather than in the symbol.

Three correctness decisions from v1.4 still worth knowing, because they are the difference between a chart and an instrument:

  • Event durations are clipped to the window and overlaps merged before summing, with the footer disclosing when merging changed the total. An unclipped, double-counted downtime figure ends up in a report.
  • Writes are treated as irreversible — validated before sending, confirmed with a human, never cached or retried, and reported per row so a partial success reads as one.
  • Shared acknowledgement verifies after writing. Read-merge-write alone lost an acknowledgement every time two operators acted at once; PI Web API has no compare-and-swap, so the write checks that it survived and retries if it did not.

What next

Nothing on this plan is outstanding. The next step is deployment, not development. None of the PI Web API symbols has run against a real PI Web API yet; they are verified against mocks that were deliberately misconfigured six ways, which is a good proxy and is not the same thing. Run ext/piwebapi-check.html on a PI Vision server, put the result into libraries/pvx-config.js on every server, deploy the read-only pvxEventGantt to one display, and let it run before anything writes.

And a broader one: 30 symbols is a large palette to introduce at once. There is a good argument for putting what exists in front of operators, finding out which symbols people actually place on displays, and letting that decide what gets built next — rather than this page deciding it. A symbol nobody places is worse than one that was never written, because it still has to be maintained.
